# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Whippet is a keyboard-driven macOS launcher (Swift 6, SwiftUI + AppKit, macOS 15+). It's a menu bar app
(`LSUIElement`) with no Dock icon.

## Commands

The `justfile` wraps the commands below: `just build`, `just run`, `just stop`, `just test [Suite/test]`, `just format`,
`just lint`, `just open`, `just clean` and `just beta` (see Betas). Each one that builds regenerates the project first.

The Xcode project is generated by XcodeGen from `project.yml` and isn't committed. Regenerate it after adding,
removing or renaming files, or after changing `project.yml`:

```sh
xcodegen generate
```

Run all tests the way CI does, without signing:

```sh
xcodebuild test -project Whippet.xcodeproj -scheme Whippet -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO
```

Run one suite or one test (Swift Testing; the identifier is the struct name, then the function name without
arguments):

```sh
xcodebuild test ... -only-testing:WhippetTests/UnitConversionTests
xcodebuild test ... -only-testing:WhippetTests/UnitConversionTests/rates
```

Build and run the development app, which is a separate app called **Whippet Dev** (`codes.dibble.whippet.dev`, yellow
menu bar icon, data in `~/Library/Application Support/Whippet Dev`, CloudKit's Development environment), so it runs
beside an installed release:

```sh
pkill -x "Whippet Dev"
xcodebuild build -project Whippet.xcodeproj -scheme Whippet -configuration Debug -destination 'platform=macOS' -derivedDataPath build/dev
open "build/dev/Build/Products/Debug/Whippet Dev.app"
```

Build the shared core on its own for iOS, to check it still uses nothing Mac-only:

```sh
cd Packages/WhippetCore
xcodebuild build -scheme WhippetCore -destination 'generic/platform=iOS'
```

Formatting and linting use swift-format, which comes with Xcode, configured by `.swift-format` (4-space indents,
120 columns). CI fails on any lint warning. Format, then lint, before committing:

```sh
git ls-files -z '*.swift' | xargs -0 xcrun swift-format format --in-place --parallel
git ls-files -z '*.swift' | xargs -0 xcrun swift-format lint --strict --parallel
```

swift-format neither wraps comments nor flags long ones, so keep new comments within 120 columns by hand.

SourceKit in editors often reports `No such module` and errors on `/…/` regex literals. These are false alarms; trust
`xcodebuild`.

## Architecture

The Mac app is in `Sources/Whippet`. What another app could share lives in the **`WhippetCore`** Swift package in
`Packages/WhippetCore`: `ClipboardStore`, `CloudSync`, quicklinks (`Quicklink`), the calculator with unit, currency,
base and time conversion, exchange rates, and `FuzzyMatch`. It uses no AppKit, builds for macOS and iOS, and exposes
only what the app uses as `public`. The app chooses where data lives (`ClipboardStore.defaultDirectory`, set in
`Modules/Clipboard/ClipboardHistory.swift`) and passes it in.

- **`AppDelegate`** owns the floating search panel (`LauncherPanel`, an `NSPanel`), the global hotkey
  (KeyboardShortcuts) and the shared services, and builds the modules from them (`makeModules()`). `WhippetApp` holds
  the SwiftUI scenes (settings and other windows).
- **Modules**: every feature is a module in `Sources/Whippet/Modules/<Name>/`: a manifest declaring its commands,
  features and what each uses (`Permission`), listed in `ModuleRegistry.all`, and a `LauncherModule`. The host lists
  each command in the main search from the manifest; the module adjusts or hides those rows (`row(for:_:)`), adds
  rows that come and go (`contributions(for:)`), offers actions on them, opens its own screens (`LauncherScreen`),
  starts and stops its own work, and supplies its settings pane. A command's hotkey runs its row's first action. Logic with no app-only dependencies
  goes in the module's `Core/` folder, which the tests compile. A beta module declares `stage: .beta` in its manifest.
  `ModuleSettings` holds the switches in Settings › Commands, and what's off does no work. Anything sensitive
  (network, Accessibility, Screen Recording, Apple Events, notifications) goes through `PermissionGate` in
  `Sources/Whippet/Permissions/`, which checks the use is declared and on; `scripts/check-permissions.sh`, run by
  `just lint` and CI, fails on those APIs anywhere else. See `docs/modules.md`.
- **The launcher** (`Sources/Whippet/Launcher/`): `LauncherModel` is the host. It holds the query, the selection, the
  stack of screens with the main search (`RootScreen`) at the bottom, and text asked for in the bar (`InputRequest`).
  Rows are `LauncherItem`s, each module's own value in `payload`. The host runs whatever `ItemAction`s the top screen
  offers for the selection: Return runs the first, ⌘Return the second, ⌘K lists them all, and it handles their
  `ActionOutcome`. It knows nothing of what any module does. `SearchView` draws the bar and the screen's content.
- **Ranking**: `LaunchHistory` and `Ranking` order results by how often and how recently they were used, alongside
  `FuzzyMatch`.
- **Calculator and unit conversion**: `Calculator.calculate` tries an expression, then a plain number, then another
  base, `UnitConversion.convert`, currency, time and finally an amount worked out without a target. Unit conversion
  is built on the `Units` package, with our own aliases and extra units.
  `looksLikeConversion` keeps the calculator showing while a conversion is still being typed.
- **Clipboard**: `ClipboardStore` is a GRDB SQLite database with an FTS5 index, plus content-hashed image files beside
  it. It also stores calculator history. `ClipboardHistory` watches the pasteboard and `Paster` pastes into the
  previous app, which needs the Accessibility permission.
- **`CloudSync`** syncs clipboard and calculator history through `CKSyncEngine` in the private database. It's
  end-to-end encrypted: record names are keyed hashes, and all fields are in `encryptedValues`. Feedback goes to the
  public database (`Feedback.swift`). The schema and security roles are in `docs/cloudkit.md`.
- **Extensions**, a beta module, run JavaScript with React in JavaScriptCore, one context per extension (`ExtensionRuntime` in
  WhippetCore). Whippet's runtime in `Extensions/api` renders to plain objects with `react-reconciler`, and each
  commit's top view goes to Swift as JSON (`ExtensionView`). `ExtensionManager` finds, watches and enables extensions,
  and `ExtensionSession` holds an open view command. The bundled runtime,
  `Packages/WhippetCore/Sources/WhippetCore/Resources/ExtensionRuntime.js`, is committed: after changing
  `Extensions/api/src`, run `npm install && npm run build` there. See `docs/extensions.md`.
- **Changelog**: `CHANGELOG.md` is bundled as a resource and parsed at runtime (`Changelog.swift`) for the Changelog
  command and What's New. It must keep the Keep a Changelog format: `## [x.y.z] - date`, `###` sections, and `- `
  items whose wrapped lines are indented by two spaces.

### Tests

The test target doesn't load the app, so tests never open the real database or start iCloud sync. It depends on
`WhippetCore`, which tests reach with `@testable import WhippetCore`, and compiles the launcher's core, every
module's manifest and every module's `Core/` folder, listed in `project.yml` under `WhippetTests.sources`. Put a
module's testable logic in its `Core/` folder, free of app-only dependencies. Contributions and the main search are
tested against `FakeHost` and `FakeModule` in `RootScreenTests`.

## Conventions

- **Localization**: strings live in `Sources/Whippet/Localizable.xcstrings`, and the core's in
  `Packages/WhippetCore/Sources/WhippetCore/Localizable.xcstrings`, looked up with `String(localized: "…", bundle:
  .module)`. English is the source language and Farsi (`fa`) the only translation. When you add a user-facing string,
  add its `fa` translation too.
- **Comments**: doc comments are full sentences explaining *why*, with examples in backticks. Match the density and
  tone of the surrounding code.
- **Dependencies** in `project.yml` and `Packages/WhippetCore/Package.swift` are pinned to exact commits on purpose.
  GRDB is in both, at the same commit. GitHub Actions are pinned to full SHAs with a version comment.
- **Beta modules**: an unfinished module declares `stage: .beta(summary:)` in its manifest. It's off by default,
  turned on under Settings › General › Beta Features (`featureFlag.<module id>` in user defaults), and does no work
  while it's off: `ModuleSettings.isEnabled` is false for all of it until then, and its module's `update(_:)` runs
  whenever a flag changes.
- **Commits** use Conventional Commits (`feat:`, `fix:`, `ci:`, `chore:`) and go straight to `main`. User-visible
  changes get an entry under `## [Unreleased]` in `CHANGELOG.md`.

## Releasing

`.github/workflows/release.yml` runs when a commit titled `chore: release X.Y.Z` is pushed to `main`. That commit:

1. Renames `## [Unreleased]` in `CHANGELOG.md` to `## [X.Y.Z] - YYYY-MM-DD`, keeping an empty Unreleased heading above
   it, and updates the compare links at the bottom.
2. Sets `MARKETING_VERSION` in `project.yml` to `X.Y.Z`.

The workflow refuses a version that doesn't match, has no changelog section or is already released. It runs the tests,
then builds, signs, notarizes and publishes the DMG and a Sparkle `appcast.xml`, with the changelog section as the
release notes and a `vX.Y.Z` tag. A run takes about 15 minutes.

### Betas

`just beta` runs the same workflow by hand on the current branch, which must be pushed (or use Actions › Release › Run
workflow). The version is the next minor version with the commit's short hash, such as `1.4.0-beta.d226ff9`, so nothing
in `project.yml` or `CHANGELOG.md` changes: the notes are the Unreleased section. It's published as a GitHub
prerelease with only the DMG, so testers install each beta by hand, and no appcast points at it.

Build numbers follow the version (`major × 1000000 + minor × 10000 + patch × 100`, plus 99 for a release), so Sparkle
moves a beta to its release, never to an older release such as a fix for the version before. A beta isn't recorded as
the last version run, so What's New after its release counts from the release before.
